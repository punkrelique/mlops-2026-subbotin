# Датасет оттока клиентов

**Источник:** генератор `src/data/generate.py`, сид из `params.yaml`.
В боевом проекте здесь была бы выгрузка из биллинга.

**Владелец:** кто отвечает за данные и к кому идти с вопросами.

**Обновление:** как часто приходит новая порция.

## Поля

| Поле | Тип | Единица | Диапазон | Комментарий |
|---|---|---|---|---|
| tenure_months | int | месяцы | 1–72 | стаж клиента |
| monthly_charges | float | руб./мес | 15–180 | текущий тариф |
| total_charges | float | руб. | >= 0 | пусто у клиентов первого месяца |

Заполните таблицу по всем колонкам.

## Известные дефекты

- `total_charges` пустой примерно у 1 % строк — это не шум, а клиенты,
  у которых ещё не было ни одного списания

## deps стадии train: Что будет, если убрать `src/features.py` из `deps` стадии `train`, и почему это опаснее обычной ошибки

DVC решает, нужно ли перезапускать стадию, только по хэшам файлов, перечисленных в `deps`.
Если `src/features.py` убрать из списка, изменения в нём не меняют хэш зависимостей стадии `train`. `dvc repro` увидит, что по его данным ничего не изменилось,
пропустит обучение и оставит старый `models/model.joblib`, обученный ещё по прежней версии препроцессора. При этом `dvc status` покажет пайплайн как актуальный,
а `src/train.py` в это время импортирует уже новую версию `build_preprocessor` из `features.py`: если потом кто-то запустит `python -m src.train` руками,
модель и код разойдутся без ошибки

Это опаснее падения скрипта, потому что ошибка, роняющая скрипт, видна сразу,
а несогласованность deps не падает и не предупреждает.
Модель в `models/model.joblib` перестаёт соответствовать коду в `src/features.py`, метрики в отчетах продолжают выглядеть нормально,
и узнать об этом можно только случайно, когда модель в проде начнёт вести себя не так, как ожидается от текущего кода.
Отсутствие сигнала об ошибке делает проблему дольше по времени обнаружения и дороже по последствиям
